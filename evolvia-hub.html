Evolvia Hub : des agents IA au service d'une équipe, avec revue humaine

Le Hub est l'outil interne d'Evolvia, développé avec mes associés. Les associés y confient des missions à des agents IA, et chaque livrable passe par une revue humaine. Ma part : la conception du module Prospection (modèle de données, collecte, scoring), proposée en 2 PR puis reprise par un associé, en m'appuyant sur mon agent de prospection.

01Le problème métier

Mon agent de prospection fonctionnait seul, à côté des outils de l'équipe. Le Hub d'Evolvia, lui, réunit déjà les missions, les agents et les règles de l'équipe, avec un principe : toute mission confiée à un agent se termine par une revue humaine. Il fallait faire entrer la prospection dans ce cadre commun, au lieu de garder un outil isolé.

02Ma contribution

PR 1 · modèle de données et collecte

  • Le schéma du module : entreprises, contacts, sites, pages, signaux, exclusions, et une liste de blocage en ajout seul, protégée par un déclencheur SQL.
  • Un sourcing sur plusieurs profils de cible à la fois, à la demande d'un associé, avec dédoublonnage par SIREN.
  • La recherche de site avec preuve et la lecture respectueuse des sites, reprises de mon agent.

PR 2 · scoring par mission déléguée

  • Aucun appel direct à un modèle depuis l'application, conformément aux règles du Hub : la qualification est confiée à un agent sous forme de mission.
  • Le livrable de l'agent est validé dès sa soumission : schéma, critères complets, signaux cités existants. L'agent peut corriger et resoumettre.
  • Le score n'est écrit qu'après la validation de la mission par un associé : pas de raccourci pour la prospection.

Pour être précis : mes deux PR n'ont pas été fusionnées telles quelles. Un associé a repris la conception et livré le module en production. Le Hub tourne sur le serveur d'un associé ; les autres modules sont le travail de l'équipe.

03Architecture du scoring

04Extrait de code

La règle « pas de signal, pas de point » appliquée au livrable de l'agent. Un seul aller-retour en base vérifie à la fois que chaque signal cité existe et qu'il appartient bien à l'entreprise notée.

Ma PR 2 · validation du livrable de qualificationTypeScript
// Un score > 0 doit citer au moins un signal_id (pas de signal → pas de point).
for (const entry of payload.breakdown) {
  if (entry.raw_score > 0 && entry.signal_ids.length === 0
      && !CRITERIA_WITHOUT_SIGNAL_REQUIREMENT.has(entry.critere)) {
    return { ok: false, error: `Critère « ${entry.critere} » : un score > 0 doit citer au moins un signal_id.` };
  }
}
// Existence ET appartenance à cette entreprise, en une seule requête.
const citedIds = [...new Set(payload.breakdown.flatMap((b) => b.signal_ids))];
const own = new Set((await db.select({ id: prospectSignals.id }).from(prospectSignals)
  .where(and(eq(prospectSignals.companyId, companyId), inArray(prospectSignals.id, citedIds))))
  .map((r) => r.id));
for (const id of citedIds) {
  if (!own.has(id)) return { ok: false, error: `signal_id inexistant ou n'appartenant pas à cette entreprise : ${id}.` };
}

06Ce que j'ai appris

  • Respecter les règles d'un système existant. J'aurais pu écrire le score dès la soumission, plus simple. Cela aurait contourné, pour la première fois, la revue humaine de toutes les missions. J'ai choisi de m'y plier et de le signaler comme décision à relire.
  • Une PR est aussi un document. Résumé, décision à relire en priorité, limites connues, plan de test : c'est ce qui rend une conception reprenable par quelqu'un d'autre, et c'est ce qui s'est passé.
  • Livrer en petites étapes empilées. Données et collecte d'abord, scoring ensuite : chaque PR se relit seule.
