Étude de cas 1 · projet principal

Plateforme d'exploitation d'une PME de transport, et son serveur MCP RH

Une PME de transport routier (~100 salariés) gérait ses tournées, ses intérimaires et sa paie dans des classeurs Excel ressaisis à la main. Pendant mon stage, de juin à septembre 2026, je lui ai construit une plateforme web et un connecteur MCP qui ouvre son SIRH à Claude. Je les fais évoluer depuis, en mission via Evolvia.

01Le problème métier

Chaque jour, des dizaines de tournées partent avec un chauffeur et un véhicule. L'information était éparpillée : un classeur Excel par mois pour les tournées, des feuilles d'heures d'intérimaires sur papier, des heures supplémentaires recopiées pour la paie, des contrôles véhicules sans suivi. Les premiers outils automatisés étaient des workflows n8n, devenus fragiles.

  • Ressaisie : la même information tapée deux ou trois fois, dans des fichiers différents.
  • Erreurs qui coûtent cher : une heure mal recopiée se retrouve sur la fiche de paie ou la facture d'une agence d'intérim.
  • Aucune vue d'ensemble : savoir qui est absent, quelle tournée n'est pas couverte, quel véhicule n'a pas été contrôlé demandait d'ouvrir plusieurs outils.

02Ce que j'ai construit

La plateforme

  • Saisie des tournées sur mobile, avec contrôles côté serveur : chauffeur et plaque obligatoires, plaque vérifiée contre le registre des véhicules, relais matin et après-midi.
  • Feuilles d'heures d'intérimaires signées sur téléphone, horodatées, puis récapitulatif hebdomadaire préparé pour chaque agence d'intérim.
  • Heures supplémentaires → récap paie : un seul calcul fait foi, réutilisé par l'export Excel.
  • Véhicules : contrôles, signalements de défauts vers l'atelier, cuves de carburant.
  • Congés croisés avec le planning : qui est absent, quelles tournées sont à couvrir.
  • 16 tâches planifiées : alerte si une tournée n'est pas saisie, contrôle GPS des tournées, rappels de congés obligatoires.

Le serveur MCP RH

Un serveur Model Context Protocol expose le SIRH de l'entreprise en lecture seule à travers 11 outils : salariés, absences, soldes de congés, feuilles de temps, planning. Deux clients l'utilisent : la plateforme, pour le planning des congés, et Claude, pour répondre en langage naturel à des questions RH.

Son authentification (octobre 2026)

  • Jeton de service pour la plateforme, comparé en temps constant.
  • OAuth 2.1 avec PKCE (S256) obligatoire pour Claude : code à usage unique valable 5 minutes, adresses de retour limitées aux domaines de Claude.
  • Jetons hachés : seule leur empreinte SHA-256 est stockée, et le jeton de rafraîchissement change à chaque usage.
  • Anti-force brute : blocage après 5 échecs par adresse et 20 au total en 15 minutes.
  • Pas de démarrage ouvert : sans secret configuré, le serveur refuse de démarrer. 25 tests automatisés.

Où est l'IA ? La plateforme elle-même n'appelle pas de modèle de langage : c'est de l'automatisation. L'IA intervient à deux endroits : le connecteur MCP, qui donne à Claude un accès contrôlé aux données RH, et la façon de développer, avec Claude Code comme agent (488 commits co-signés).

04Sources de données et intégrations

Inventaire tiré du code : 4 services externes appelés par API en production, et 2 sources par fichier. Pour chacune, ce qu'elle apporte, comment elle est branchée, et le problème technique qu'il a fallu régler.

Eurecia · SIRH

MCP · API REST
Apporte
Salariés, absences et congés, feuilles de temps, planning. En lecture seule.
Méthode
L'API REST d'Eurecia est enveloppée par mon serveur MCP (JSON-RPC tools/call). La plateforme et Claude passent tous les deux par lui, jamais directement par l'API.
Problème résolu
Authentification à deux étages : le serveur échange sa clé contre un jeton de session de 25 minutes, renouvelé automatiquement ; ses propres clients présentent un jeton de service ou passent par OAuth. Pagination : l'API rend 50 salariés par page, un outil dédié parcourt toutes les pages pour couvrir tout l'effectif. Rapprochement : le SIRH mélange comptes de personnes et comptes de tournées ; chaque absence est rattachée d'abord à une tournée, sinon à une personne par comparaison de noms tolérante.

Optimum Automotive · télématique

API REST · OAuth 2
Apporte
Le GPS de la flotte : trajets de chaque véhicule, registre des véhicules et kilométrages, fiches conducteurs, lignes de coût. En écriture, la fiche conducteur d'un nouvel intérimaire est créée automatiquement.
Méthode
API REST, OAuth 2 en client credentials. Synchronisation chaque nuit, plus des appels à la demande.
Problème résolu
Quotas : un délai minimal par point d'accès et une reprise sur erreur 429 qui respecte Retry-After ; la synchro de nuit interroge ~300 véhicules un par un en une douzaine de minutes. Absence de donnée ≠ zéro : un véhicule dont l'appel a échoué est marqué « non scanné », jamais « immobile ». Rapprochement : noms GPS et noms des feuilles d'heures comparés malgré l'ordre des mots et les fautes de frappe ; plaques saisies à la main vérifiées contre la flotte, avec une réponse à trois états (connue, inconnue, indéterminée).

Microsoft 365 · Graph

Graph · OAuth 2
Apporte
La GED SharePoint : contrats des intérimaires, dossiers véhicules, archives des signalements et exports paie. Dans Outlook, les brouillons du récap hebdomadaire de chaque agence d'intérim.
Méthode
API Microsoft Graph, OAuth 2 en mode application, jeton mis en cache et renouvelé avant expiration.
Problème résolu
Pagination : les dossiers sont listés en suivant @odata.nextLink, avec $select pour ne ramener que le nom et le type. Rapprochement : les noms des fichiers de contrats sont saisis à la main et leur orthographe varie ; le bon contrat est retrouvé par distance d'édition. Les brouillons ne partent jamais seuls : une personne relit et envoie.

Envoi de mails · Gmail

SMTP
Apporte
Les alertes et récaps des tâches planifiées : tournée non saisie, contrôle GPS du matin, dépassement d'horaire, échéances.
Méthode
SMTP via Nodemailer, avec un mot de passe d'application.
Problème résolu
Idempotence : l'alerte de dépassement d'horaire est envoyée une seule fois par personne et par jour, même si la tâche repasse. Contrôle : chaque type de mail a son interrupteur de configuration (12 au total), pour couper un envoi sans redéployer.

Classeurs Excel maîtres

Fichier
Apporte
Le suivi mensuel des tournées, que l'exploitation continue d'utiliser.
Méthode
Lecture et écriture de fichiers .xlsx (Python avec openpyxl, Node.js avec ExcelJS).
Problème résolu
Le classeur du mois est créé automatiquement à partir du précédent, sans casser ses formules matricielles ; chaque saisie retrouve sa ligne par la référence de la tournée.

Exports de cartes carburant

Fichier
Apporte
Les pleins par véhicule, qui alimentent l'alerte de consommation (kilomètres parcourus entre deux pleins).
Méthode
Import d'un export Excel.
Problème résolu
Deux formats d'export coexistent : la ligne d'en-tête est détectée dynamiquement (l'un des formats commence par un bandeau de quatre lignes) et les colonnes sont reconnues par alias.

Où passe Claude ? Uniquement par le serveur MCP, vers le SIRH, en lecture seule. Les autres sources ne sont accessibles qu'à la plateforme.

05Extraits de code

Deux extraits courts. Le premier vient d'un incident réel : renvoyer une journée de tournées avec une seule ligne remplie effaçait les autres sans prévenir. Les saisies ont été restaurées, puis le serveur a reçu ce contrôle.

Plateforme · route d'enregistrement d'une journée de tournéesJavaScript
// Effacement partiel : l'envoi ne couvre pas des tournées déjà saisies.
// Un envoi remplace la journée entière ; sans ce contrôle, renvoyer une
// journée avec une seule tournée renseignée efface les autres sans le dire.
if (!b.confirme_suppression) {
  const eff = tournees.detecterEffacement(id, b.date, b.rows);
  if (eff) {
    return refuser(409, { ok: false, code: 'effacement_partiel',
                         error: eff.message, tournees: eff.tournees });
  }
}
Serveur MCP · échange du code OAuth contre un jetonJavaScript
const cle = sha256(p.code || "");
const entree = codes.get(cle);
codes.delete(cle); // usage unique, même en cas d'échec
const verifie = entree && entree.expire > Date.now()
  && entree.clientId === p.client_id
  && entree.redirectUri === p.redirect_uri
  && p.code_verifier
  && egal(crypto.createHash("sha256").update(p.code_verifier).digest("base64url"),
          entree.challenge);   // PKCE S256, comparaison en temps constant
if (!verifie) { json(res, 400, { error: "invalid_grant" }); return true; }
json(res, 200, delivrer(entree.clientId)); // jetons stockés sous forme d'empreinte

07Ce que j'ai appris

  • Un garde-fou côté serveur vaut mieux qu'une consigne. Le formulaire empêchait déjà la plupart des erreurs ; c'est le contrôle serveur qui protège contre le formulaire resté en cache sur un téléphone.
  • Un calcul qui fait foi doit vivre à un seul endroit. Les heures supplémentaires sont calculées par un seul module, que la page, le récap et l'export réutilisent. Deux copies finissent toujours par diverger, et c'est la paie qui le paie.
  • L'ordre de déploiement fait partie de la solution. Pour sécuriser le serveur MCP sans coupure, la plateforme a d'abord envoyé son jeton, puis le serveur a commencé à l'exiger. Ensuite, vérification en production : refus sans jeton, congés toujours chargés.
  • L'adoption se joue sur le téléphone. Les vérificateurs saisissent sur le terrain : chaque écran est pensé pour le mobile, et chaque rôle ne voit que ce qui le concerne.
